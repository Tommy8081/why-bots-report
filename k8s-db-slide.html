Architecture Review

K8s 下的数据库连接：业界怎么做，我们怎么做

前端 TypeScript　·　后端 Node TS　·　从 SOAP 网关走向认证代理与连接池
库只被一个受控服务访问 —— 方向对
业界怎么做（五种主流做法）
托管库 + 认证代理 代理跑在 Pod 里，用工作负载身份换凭据，没有长期密码 Cloud SQL Proxy / RDS Proxy
连接池中间件 Pod 再多，落到库上的连接数是常数，不会随扩容线性翻倍 PgBouncer / ProxySQL
凭据不进镜像 Secret 只是引用，真实值由 Vault / 外部密钥系统运行时注入 External Secrets · Vault CSI
私有网络 + mTLS 库不开公网；NetworkPolicy 默认拒绝，只放行应用的 5432/1433 NetworkPolicy · Istio / Linkerd
数据库也放进集群 —— 不得已才这么干 数据不能出机房时用 Operator 管主从与备份（CloudNativePG / Vitess），别手写 StatefulSet，别用 NFS
我们怎么做（目标形态）
浏览器 · 前端 TS静态资源，只认后端 API
HTTPS
Node TS · K8s 多副本进程级连接池，max 由副本数反推
SOAP/XML 换成 gRPC 或 JSON
C# 业务服务（保留）业务规则在这里就留着；凭据由平台注入
私有网络 · TLS 校验 · 最小权限账号
SQL Server · 私有子网只接受应用网段；审计与慢查询可见
若 C# 只是拼 SQL 转发的薄代理 → 直接拆掉，Node 连托管库
凭据不再押一台机器身份换取短命凭据，轮换不用重启
连接数可预测扩容不再打爆数据库，池削峰
延迟看得见链路埋点，SQL 慢查询能定位
改造可灰度按接口切换，每一步能回滚
一句话：保留「库只由一个受控服务访问」的边界，换掉 SOAP 这个传输，把凭据从机器上挪到平台里。
