前端 TS + 后端 Node TS 上 K8s
数据库到底该怎么连

你现在的链路：TS → Node → SOAP → C# 服务 → DB。下面先给结论，再给业界五种主流做法、安全清单、代码与清单要点、迁移路线。

① 结论 ② 你现在的链路 ③ 业界五种做法 ④ 安全清单 ⑤ Node 侧写法 ⑥ K8s 清单 ⑦ 决策树 ⑧ 迁移路线 ⑨ 十个坑

1一句话结论

方向对，传输和凭据这两处不对。

「应用不直连数据库、由一个服务统一收口」正是业界主流思路——它把连接池、权限、审计收到一处，Node 侧不散落 SQL。
错的是两点：把 SOAP/XML 当作内部传输（重、难观测、Node 侧没有连接池控制权），以及数据库凭据押在那台 C# 服务器上（它成了唯一的「能进库的人」，也成了唯一瓶颈和最大打击面）。

✅ 保留的

  • 「数据库只被一个受控服务访问」这个边界
  • C# 服务里已有的业务规则、校验、审计
  • 前后端分离，前端只认后端 API

❌ 要换的

  • SOAP/XML → gRPC 或 JSON/HTTP（内部通信）
  • 手写连接串 → 托管认证代理 / 动态凭据
  • 单台 C# 服务器 → 无状态多副本 + 受限网络
  • 「C# 服务 = 薄 SQL 代理」这种形态 → 直接去掉

注意：这里不是说 C# 不该存在。下面第 7 节给了一条判断线——它到底是「业务服务」还是「SQL 代理」，两种命运完全不同。

3业界现在怎么连：五种做法，按普及度排

共同点：数据库永远在私有网络里，应用永远不持有长期静态口令，连接由「代理 + 池」治理。

最主流 托管数据库 + 云厂商认证代理

AWS RDS Proxy / GCP Cloud SQL Auth Proxy / Azure 私有终结点

  • 代理跑在 Pod 里做 sidecar 或单独 Deployment，应用连 127.0.0.1:5432
  • 凭据用工作负载身份（IAM / Workload Identity / Entra ID）换取，没有长期密码
  • 代理负责 TLS、连接复用、故障切换时的重连

适合：用云托管数据库（绝大多数公司）。这是现在的默认答案。

最主流 连接池中间件

PgBouncer / PgCat / ProxySQL / RDS Proxy 自带池

  • K8s 里 Pod 数量随 HPA 变，连接数会乘法级增长，必须有池把前端连接压成后端少量长连接
  • PgBouncer 用 transaction 模式；注意事务里跨语句的会话状态（临时表、advisory lock）会失效
  • 没有池，一次大促或一次 HPA 抖动就能把数据库连接打满

适合：Pod 数 > 3 或数据库连接上限 < 500 的任何场景。

标配 凭据不进镜像：外部密钥

External Secrets Operator / Vault + Secrets Store CSI / Sealed Secrets

  • Secret 只是「引用」，真实值由外部系统在运行时注入或挂载
  • 比 env 明文强：env 会出现在 kubectl describe pod、崩溃转储、子进程环境里
  • 理想终点是动态凭据（Vault 数据库引擎每次发一个短命账号）

按需 零信任网络：私有子网 + mTLS

NetworkPolicy 默认拒绝 / Istio、Linkerd mTLS / PrivateLink

  • 数据库不暴露任何公网入口；只允许来自特定 namespace + 标签的 Pod 访问
  • 服务间用 mTLS，外部只能经 Ingress / API 网关进来
  • NetworkPolicy 需要 CNI 支持（Calico、Cilium 等）

不得已 数据库也放进集群

CloudNativePG / Zalando Postgres Operator / Vitess

  • 只有数据不能出本机机房、或合规要求时这么做
  • 必须用 Operator 管主从、备份、PITR；手写 StatefulSet 基本等于自找事故
  • 存储用本地 SSD / 云盘 CSI，别用 NFS 跑数据库

一张对照表：你的 SOAP 网关 vs 上述做法

维度现在的 SOAP + C# 服务业界主流
凭据静态口令，位于一台服务器工作负载身份换取短命凭据
连接管理由 C# 服务自己管池，Node 无控制权专用池（PgBouncer/RDS Proxy）+ 应用内池
传输XML/SOAP，体积大、解析慢、易踩 XXE二进制协议（TDS/Postgres）或 gRPC
可观测只能看到 HTTP 500，看不到 SQL 耗时OpenTelemetry 自动埋点 + 池指标
弹性整台复制，连接数线性涨无状态多副本 + 池削峰
权限模型一个高权限账号，全库可读按服务/按表最小权限，读写分账号
故障面C# 服务挂 = 全部业务挂代理与副本冗余，连接自动重试

4安全清单：六件事，做到就算及格

① 凭据

  • ✅ 用 ExternalSecret / CSI 挂载，或干脆 IAM 认证
  • ✅ 定期轮换，应用能热加载
  • ❌ 不要把密码写进镜像、ConfigMap、前端、注释
  • ❌ 不要 POSTGRES_PASSWORD 这种直接 env 塞（会被 describe 看到）

② 网络

  • ✅ 数据库在私有子网，安全组只放行应用所在节点/网段
  • ✅ NetworkPolicy 默认 deny，白名单放行出站到 DB 的 5432/1433
  • ❌ 不要 0.0.0.0/0 放行数据库端口
  • ❌ 不要把 DB 端口做成 NodePort / LoadBalancer

③ 传输加密

  • ✅ Postgres：sslmode=verify-full（不是 require）
  • ✅ SQL Server：encrypt=true;trustServerCertificate=false
  • ✅ 内部 SOAP 也上 TLS，并校验服务端证书
  • ❌ 不要为了方便关闭证书校验

④ 权限

  • ✅ 一服务一账号，只授需要的 schema/表/动作
  • ✅ 迁移账号与运行账号分离，迁移只在 Job 里用
  • ❌ 不要用 sa / postgres / root 跑应用
  • ❌ 不要让应用账号有 DDL 权限

⑤ 连接数

  • ✅ 应用池 max = (DB 上限 − 保留) ÷ 最大副本数
  • ✅ PgBouncer 兜一层，Pod 再扩也不炸库
  • ❌ 不要 50 副本 × 每副本 20 连接 = 1000 直接越过 DB 上限

⑥ 审计与观测

  • ✅ OpenTelemetry 自动埋点 pg/mssql，看 P95 与慢查询
  • ✅ 记录谁在什么时间改了哪张表（关键表触发器或审计日志）
  • ❌ 不要只有一句「500 Internal Error」

5Node TS 侧：池怎么配，关闭怎么做

// db.ts —— 一个进程一个池，别每次请求 new Client
import { Pool } from 'pg'

export const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: Number(process.env.PG_POOL_MAX ?? 10),   // 见下面公式
  idleTimeoutMillis: 30_000,                    // 空闲回收，避免被 DB 端掐断
  connectionTimeoutMillis: 5_000,
  statement_timeout: 15_000,                    // 单条 SQL 上限，防慢查询拖死池
  query_timeout: 15_000,
  ssl: { rejectUnauthorized: true },            // 必须校验证书
  application_name: 'svc-order-api',            // DB 端能看出是谁
})

pool.on('error', (e) => console.error('idle client error', e))

每 Pod 连接数公式

每 Pod 池上限 = (DB max_connections − 运维保留 20) ÷ 最大副本数
例：DB 100 连接、最大 8 副本 → (100 − 20) ÷ 8 = 10

优雅关闭（K8s 会先发 SIGTERM，再等 terminationGracePeriodSeconds）

process.on('SIGTERM', async () => {
  server.close()                 // 先停止接新请求
  await sleep(3_000)             // 让 readiness 生效，LB 摘流量
  await pool.end()               // 再关连接池
  process.exit(0)
})

补充：Drizzle / Prisma / Kysely 都支持外部传入 pool 或连接串；Prisma 在 K8s 里建议配 connection_limit 与 PgBouncer 的 pgbouncer 模式参数。ORM 不是安全层——SQL 注入靠参数化查询，不靠 ORM。

6K8s 清单要点

Deployment

readinessProbe:            // 池能连上 DB 才 Ready
  exec: { command: ["node","-e","require('./dist/db').ping()"] }
  periodSeconds: 10
lifecycle:
  preStop: { exec: { command: ["sleep","5"] } }
terminationGracePeriodSeconds: 30
strategy: { rollingUpdate: { maxUnavailable: 0 } }

为什么：Pod 一启动就接流量，池还没建好 → 首屏 500；SIGTERM 立刻退出 → 正在跑的 SQL 被杀。

Secret 引用

# 推荐：外部密钥，Secret 只是占位
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
spec:
  secretStoreRef: { name: vault, kind: ClusterSecretStore }
  target: { name: db-app }
  data:
    - secretKey: DATABASE_URL
      remoteRef: { key: prod/order-api/db-url }

挂成文件（volume）比 env 好：不会进 /proc、不进子进程环境、不被打进崩溃转储。

NetworkPolicy

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: order-api }
spec:
  podSelector: { matchLabels: { app: order-api } }
  policyTypes: ["Egress"]
  egress:
    - to: [{ namespaceSelector: { matchLabels: { name: db } } }]
      ports: [{ protocol: TCP, port: 5432 }]
    - to: [{ namespaceSelector: { matchLabels: { name: kube-system } } }]
      ports: [{ protocol: UDP, port: 53 }]   # DNS 别忘了

迁移与伸缩

  • 迁移用单独的 Job，跑完再滚动 Deployment；别塞 initContainer（多副本会并发迁移）
  • HPA 用 CPU/延迟指标，maxReplicas 必须是「DB 连接数 ÷ 每 Pod 池」算出来的值，不能拍脑袋
  • 加 PodDisruptionBudget，节点维护时不同时踢掉全部副本
  • 重启风暴会瞬间打满连接：配 backoffLimit 与连接重试抖动

7你的 SOAP 网关该留还是该拆

判断标准很简单：把 C# 服务删掉，Node 直接查库能不能得到同样的结果？能 → 它是代理，删掉；不能 → 它是业务服务，留着但换传输。

如果你的 C# 服务同时承担业务规则和 SQL，那先按业务服务保留，再逐步把查询逻辑下移——不要一次性大爆炸改造。

8迁移路线：四步，每步都能回滚

  1. 摸底（1 周）　统计现有调用量、P95 延迟、每台 C# 服务的连接数与 SQL 数；标出最热的 5 个接口。没有这组数字，后面所有改造都无法证明有效。
  2. 凭据与网络先收口（1–2 周）　C# 服务的数据口令改为平台注入；数据库只许应用网段访问；给 Node 与 C# 服务加 NetworkPolicy。这一步不改变任何业务代码，风险最低、收益最大。
  3. 传输替换（按接口灰度）　在 C# 服务外挂一层 gRPC/JSON 门面（或直接改造），Node 侧按接口切换，双写不双读，用影子流量对比结果。SOAP 保留到最后一个接口切完。
  4. 收口或下线（2–3 月）　若是薄代理，Node 改直连托管 DB + 认证代理 + PgBouncer，做一轮压测（目标：连接数不随副本线性增长）；若是业务服务，把它收成内部服务，只暴露领域接口。

验收指标（能写进周报的那种）

  • P95 端到端延迟下降多少（替换 XML 通常能看到 30%–60%）
  • 数据库峰值连接数：从「副本数 × N」变成常数
  • 新增一个 Pod 不再需要人工调连接数
  • 凭据轮换能在不重启业务的情况下完成

9十个坑，按踩到概率排

坑后果怎么避
每次请求新建连接连接数爆、延迟翻倍进程级池 + 复用
HPA 无上限扩容即打爆 DBmaxReplicas 由连接预算反推
密码写 env 明文kubectl describe 就泄露ExternalSecret 挂文件
